B. APP CONCEPT, ROLES & RBAC
==================================================

VidyaVault is a test and analytics platform for a small tuition setup in Siliguri (West Bengal, India). There are three subject teachers (Chemistry, Biology, Math) and multiple students belonging to different boards (West Bengal board, ICSE, CBSE) and mediums (English vs Bengali).

Roles:

1. `superadmin`
   - Owner of the system.
   - Can see and manage EVERYTHING across all teachers and students.
   - Responsibilities:
     - Create and manage teacher accounts.
     - Promote/demote users between roles (`superadmin`, `teacher_admin`, `student`).
     - View all tests, submissions, leaderboards, and reward cycles.
     - Configure global settings (e.g., default test duration, reward period length).

2. `teacher_admin` (teacher)
   - One account per teacher (Chemistry, Biology, Math).
   - Must NOT see any other teacher’s data.
   - Responsibilities:
     - Manage ONLY their own batches and students.
     - Create student accounts (username/password), reset passwords for their students.
     - Create and manage tests (manual or AI‑assisted).
     - View results, analytics, and leaderboards only for their own tests and students.
     - See reward outcomes for their batches.

3. `student`
   - Logs in with credentials created by a teacher or superadmin.
   - Can change own password after login (with current password verification).
   - Can attempt tests, see results with solutions, and see personal analytics and leaderboards.

RBAC and isolation requirements:

- Implement robust RBAC and strict data isolation:
  - A `teacher_admin` must NEVER be able to see:
    - Another teacher’s students.
    - Another teacher’s tests or submissions.
    - Another teacher’s analytics or leaderboards.
- Enforce this on the backend using:
  - Role checks AND
  - Ownership checks (`teacher_id`‑based) in every relevant query.
- `superadmin` can bypass all restrictions and see everything.
- `student` can only access:
  - Their own tests and submissions.
  - Limited leaderboard views (class/batch contexts they belong to).

Implementation guidelines:

- JWT payload must include:
  - `userId`
  - `role` (`superadmin`, `teacher_admin`, `student`)
  - For teachers: the teacher profile ID(s) needed for scoping (e.g., `teacherId` or `teacherIds`).
  - For students: `studentId` (for scoping).
- Implement reusable authorization helpers on the backend, such as:
  - `authMiddleware` to validate JWT and attach `req.user`.
  - `requireRole(...roles)` to guard routes.
  - Teacher‑scoped helpers, e.g., `ensureTeacherOwnsResource(teacherId, resource)`.
  - Student‑scoped helpers, e.g., ensuring a student only accesses their own submissions.

5. English vs Bengali competition logic (Reward system)

Core idea:

- For each teacher+subject over a defined period (e.g., 2 months), compare English medium vs Bengali medium batches.

Reward cycle:

- `RewardCycle` defines a period:
  - `periodStart`, `periodEnd`
  - `teacherId`, `subject`
- Only consider tests where:
  - `test.subject` equals the cycle subject.
  - `test.teacherId` equals the cycle teacher.
- Only consider submissions from:
  - Batches where `medium` is `ENGLISH` or `BENGALI`.
  - Those batches are linked to the same teacher.

Normalized scoring:

- For each student in a batch within the period:
  - Compute `normalizedScore = totalObtainedMarks / totalMaxMarks` across their submissions in that cycle.
- For each batch:
  - Compute `batchAverage = average(normalizedScore of all eligible students in that batch)`.
- Enforce minimum participation rules (configurable constants or DB‑stored settings, with TODOs if not yet configurable):
  - `minTestsPerStudent`
  - `minActiveStudentsPerBatch`

Determination:

- `TopPerformanceBatch`:
  - Batch with highest `batchAverage` that meets participation criteria.
- `MostImprovedBatch`:
  - Batch with highest increase in `batchAverage` compared to previous RewardCycle for the same teacher+subject.

Persist results:

- Create `BatchRewardResult` rows per batch in the cycle:
  - Set `averageNormalizedScore`, `improvementScore`.
  - Mark:
    - `isWinner` for the TopPerformanceBatch.
    - `isMostImproved` for the most improved batch.
- Create `StudentBadge` records for:
  - Top performers (e.g., top X students in winning batch by normalizedScore).
  - Most improved students by improvement within that cycle.

Backend services:

- Implement a `rewardService` responsible for:
  - Aggregating scores and computing normalized values.
  - Determining winners and most improved batches.
  - Writing `BatchRewardResult` and `StudentBadge` records.
- Write tests for:
  - Normalization.
  - Winner and most improved selection.
